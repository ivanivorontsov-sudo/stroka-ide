# Строка: центр сборки и каталог инструкций

## Что делает кнопка «Собрать»

Кнопка в верхней панели открывает центр сборки. Выбирается цель:
- **Автоопределение** — Android Gradle, .NET, веб-проект или Python.
- **Android APK** — debug APK, пригодный для установки и проверки.
- **Android AAB** — debug Android App Bundle для проверки сборки.
- **Windows EXE** — self-contained single-file .NET EXE для win-x64.
- **Сайт** — собирает Node-проект или упаковывает статический сайт в ZIP.
- **Python EXE** — PyInstaller one-file для Windows.

Сборка выполняется в GitHub Actions на подходящем runner: Linux для Android и веба, Windows для EXE. Это намеренно: Android-приложение не содержит полноценные Android SDK/NDK, Windows SDK и компилятор .NET для всех целевых архитектур.

## Подготовка перед сборкой

1. Откройте проект из локального Git-репозитория.
2. Настройте GitHub token в Настройки → Git и GitHub.
3. У токена должно быть право **Actions: write**; для приватного репозитория нужен доступ к репозиторию. Для классического PAT обычно требуется scope `repo`.
4. В основной ветке репозитория должен находиться `.github/workflows/project-build.yml`.
5. Сохраните изменения коммитом и отправьте их через push.
6. Убедитесь, что локальная ветка совпадает с `origin/<branch>`. Центр сборки не отправляет код без спроса и не собирает случайно устаревший commit.

GitHub принимает ручной запуск workflow через `workflow_dispatch`; параметры передаются в inputs. Подробности: https://docs.github.com/en/rest/actions/workflows и https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow.

## Поддерживаемые структуры

### Android / Kotlin / Java

Ожидается Android Gradle проект:
- `settings.gradle` или `settings.gradle.kts`;
- корневой `build.gradle` / `build.gradle.kts`;
- модульный `app/build.gradle` / `app/build.gradle.kts`;
- желательно Gradle Wrapper: `gradlew`, `gradlew.bat`, `gradle/wrapper/`.

Runner автоматически устанавливает JDK 17, Android SDK platform 36, build-tools 36.0.0, Python 3.12 (для плагинов вроде Chaquopy) и Gradle 8.9 как запасной вариант, если wrapper отсутствует. Запускается `assembleDebug` для APK или `bundleDebug` для AAB. Зависимости Gradle восстанавливаются автоматически.

Если wrapper отсутствует, сборка использует установленный Gradle. Это не гарантирует совместимость любого старого проекта: версия Android Gradle Plugin должна соответствовать версии Gradle и JDK.

Официальная документация:
- https://developer.android.com/build/building-cmdline
- https://developer.android.com/build/configure-apk-splits
- https://developer.android.com/studio/publish/app-signing

### Windows EXE (.NET)

Ожидается хотя бы один `.csproj` внутри папки проекта. Сборщик:
- устанавливает .NET SDK 8;
- выполняет `dotnet restore`;
- публикует `win-x64`, self-contained, single-file;
- проверяет наличие EXE и сигнатуру PE/MZ;
- сохраняет SHA-256.

Команда эквивалентна:
```powershell
dotnet publish App.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true
```

Single-file EXE привязан к ОС и архитектуре. Для ARM64 и x86 нужен отдельный runtime target. Self-contained файл крупнее, зато на компьютере не требуется отдельно устанавливать .NET Runtime.

Официальная документация:
- https://learn.microsoft.com/dotnet/core/deploying/single-file/overview
- https://learn.microsoft.com/dotnet/core/deploying/

### Python EXE

Ожидается `main.py`, `app.py` или `run.py`, а также при наличии — `requirements.txt`. Сборщик устанавливает Python 3.12, зависимости и PyInstaller, затем создаёт Windows one-file EXE.

PyInstaller не превращает произвольный Python-проект в универсальный кроссплатформенный бинарник: EXE создаётся на Windows runner для Windows. Для GUI-приложений, динамических импортов, DLL, Qt/Tk и файлов данных может потребоваться `.spec` и явное включение ресурсов.

### Сайты и веб-приложения

Поддерживается:
- статический сайт с `index.html`;
- Node.js проект с `package.json`;
- lockfile `package-lock.json` (предпочтителен для воспроизводимого `npm ci`);
- выходные каталоги `dist/` или `build/`.

Для статического сайта создаётся ZIP с каталогом сайта. Для Node запускается установка npm-зависимостей и `npm run build`, если скрипт существует. В артефакте должен быть `index.html`.

## Что исправляется автоматически

Сборочная машина сама обеспечивает инструменты и стандартные шаги восстановления:
- установка JDK / Android SDK / build-tools / Gradle;
- установка .NET SDK и `dotnet restore`;
- установка Python и пакетов из `requirements.txt`;
- установка Node.js и `npm ci` при наличии lockfile;
- создание выходных каталогов;
- проверка наличия ожидаемого артефакта;
- SHA-256 для результата.

## Что нельзя исправлять молча

Ошибки исходного кода — не «недостающая библиотека». Нельзя без согласования переписывать бизнес-логику, удалять функции, снижать targetSdk, отключать тесты, убирать проверку подписи или подавлять предупреждения компилятора. При ошибке компиляции программист должен увидеть:
- файл и строку, если компилятор их сообщил;
- исходное сообщение ошибки;
- какой инструмент и версия использовались;
- что сборщик уже установил или восстановил;
- безопасное предлагаемое исправление;
- что именно нужно изменить вручную.

Текущий workflow автоматически подготавливает инструменты и восстанавливает зависимости, но не выполняет генеративное переписывание исходников. Для этого нужен отдельный AI repair loop с diff-предпросмотром, тестами, ограничением числа попыток и обязательным согласием на изменение файлов.

## Контроль качества

Успешный статус компиляции ещё не означает, что приложение корректно работает. Для разных типов нужны отдельные проверки:
- APK: файл существует, пакет читается, подпись проверяется, установка и запуск на эмуляторе/устройстве.
- AAB: пакет проверяется через bundletool; AAB нельзя проверять инструментом apksigner как APK.
- EXE: PE-заголовок, архитектура, наличие зависимостей; далее smoke-test на Windows runner.
- Сайт: наличие index.html, проверка ссылок, мобильной ширины, консоли браузера и основных сценариев.

Сборочные артефакты GitHub Actions хранятся ограниченное время; срок хранения задаётся в workflow. См. https://docs.github.com/en/actions/tutorials/store-and-share-data.

# Каталог команд конструктора

## Создание

- «Создай красивую визитку» / «сделай цифровую визитку» / «business card» — премиальная адаптивная карточка контактов.
- «Создай лендинг» / «сделай главную страницу сайта» / «create a landing page» — hero, преимущества, призыв к действию и контакты.
- «Добавь заголовок», «добавь текст», «добавь картинку», «добавь кнопку», «добавь форму», «добавь калькулятор».
- «Добавь секцию услуг», «блок преимуществ», «отзывы», «частые вопросы», «команду», «галерею», «контакты».
- «Создай портфолио», «сайт компании», «страницу продукта», «страницу мероприятия», «страницу кафе».

## Редактирование

- «Выбери первый блок», «выбери второй блок», «блок три».
- «Назови заголовок ...», «измени текст на ...», «замени подпись на ...».
- «Сделай ширину 600 пикселей», «ширина 100 процентов».
- «Сделай текст крупнее», «уменьши шрифт», «сделай заголовок жирным».
- «Выровняй по центру», «по левому краю», «по правому краю».
- «Добавь отступ», «уменьши отступ», «скругли углы», «убери скругление».
- «Сделай фон тёмным», «светлый фон», «синий акцент», «минималистичный стиль», «премиальный стиль».
- «Подними блок», «опусти блок», «удали блок», «отмени последнее изменение».

## Дизайн и качество

- Один главный заголовок на экран, чёткая иерархия текста, контрастные CTA.
- Адаптивная сетка: одна колонка на узком экране, несколько колонок на широком.
- Изображения должны иметь alt-текст и не ломать пропорции.
- Кнопки и ссылки должны вести к реальному действию, а не быть декорацией.
- Формы должны иметь подписи полей, типы input, понятную валидацию и сообщение об успехе.
- Проверять клавиатурную навигацию, фокус, контраст, масштабирование и переполнение.
- Не придумывать телефон, адрес, почту, отзывы, награды или клиентов. Использовать редактируемые заглушки, если данных нет.
- Не использовать чужие фотографии и логотипы без разрешения.

## Примеры формулировок

- «Создай строгую чёрно-золотую визитку для фотографа, с портретом, кнопкой написать и ссылкой на портфолио».
- «Сделай светлый минималистичный лендинг для ремонта квартир: услуги, этапы работы, цены, отзывы, контакты».
- «Создай сайт кофейни в тёплых кофейных цветах: меню, часы работы, адрес, кнопка заказа».
- «Сделай страницу приложения: большая обложка, три преимущества, скриншоты, тарифы, FAQ и кнопка скачать».
- «Добавь блок контактов с почтой, Telegram и GitHub».
- «Сделай адаптивную карточку: на телефоне одна колонка, на компьютере две».
- «Покажи предпросмотр», «вставь HTML в редактор».

## Принцип расширения словаря

Не следует раздувать словарь повторяющимися синонимами без тестов. Для каждой новой команды нужны:
1. каноническое намерение;
2. русские и английские варианты;
3. разговорные и короткие варианты;
4. защита от случайного срабатывания внутри цитаты, кода и примера;
5. тест на положительное распознавание;
6. тест на буквальную диктовку и отрицательный сценарий.

Качество определяется точностью распознавания, предсказуемостью и тестами, а не мегабайтами повторяющихся фраз.
